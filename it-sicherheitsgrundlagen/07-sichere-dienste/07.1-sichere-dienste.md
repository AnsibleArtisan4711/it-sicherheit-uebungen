## Lernziele

Nach dieser Übung kannst du

- Administrationsdienste (wie SSH) sicher konfigurieren (Key-based Auth)
- die Bedeutung von TLS für sichere Datenübertragung kennen

## Voraussetzungen

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **Key-based Authentication** | Anmeldung mit Schlüsselpaar statt Kennwort; der private Schlüssel verlässt den Client nie |
| **`authorized_keys`** | Datei mit den erlaubten öffentlichen Schlüsseln eines Benutzers |
| **`sshd_config`** | Konfigurationsdatei des SSH-Dienstes |
| **NLA** | Netzwerkebenen-Authentifizierung: RDP prüft die Anmeldung, bevor die Sitzung aufgebaut wird |
| **TLS** | Protokoll für verschlüsselte, authentifizierte Verbindungen (Grundlage von HTTPS) |
| **Selbstsigniertes Zertifikat** | vom Inhaber selbst signiert; ohne Vertrauenskette erscheint eine Warnung |
| **Sicherheits-Header** | z. B. `Strict-Transport-Security`, `Content-Security-Policy`, `X-Content-Type-Options` (Theorie) |

## Laborumgebung

| Was | Rolle in Modul 07 |
|---|---|
| `VM-LINUX` | SSH-Server (`anna`), Testserver für TLS |
| `VM-WIN-CLIENT` | SSH-Schlüssel erzeugen, Anmeldung testen, RDP-Client |
| `VM-WIN-SRV` | RDP mit NLA, Gruppe „Remotedesktopbenutzer“ |

## Aufgabe

### Aufgabe 1 – Key-based Authentication einrichten (Passwort-Login noch aktiv) (Einheit 7.2)

Prüfe auf `VM-LINUX`, dass der SSH-Dienst läuft (`systemctl status ssh`). Erzeuge auf `VM-WIN-CLIENT` ein SSH-Schlüsselpaar (`ssh-keygen -t ed25519`), übertrage den öffentlichen Schlüssel nach `~/.ssh/authorized_keys` des Benutzers `anna` (z. B. `type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh anna@192.168.50.20 "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys"`), setze auf `VM-LINUX` die Rechte (`chmod 700 ~/.ssh`, `chmod 600 ~/.ssh/authorized_keys`) und teste den Login mit Schlüssel in einer zweiten Sitzung.

### Aufgabe 2 – SSH-Härtung (Linux) (Einheit 7.2)

Erst nachdem der Schlüssel-Login funktioniert und eine Sitzung offen ist: Konfiguriere den SSH-Daemon (`/etc/ssh/sshd_config`) auf `VM-LINUX`: `PermitRootLogin no` und `PasswordAuthentication no`. Prüfe die Syntax mit `sudo sshd -t`, lade den Dienst neu (`sudo systemctl reload ssh`) und weise nach, dass der Schlüssel-Login weiter funktioniert und der Passwort-Login scheitert (`ssh -o PubkeyAuthentication=no anna@192.168.50.20` → „Permission denied“). Diese Härtung bleibt für die Module 10 und 12 bestehen.

### Aufgabe 3 – Absicherung von Remotedesktop (Windows) (Einheit 7.1, Einheit 7.2, Einheit 7.3)

Prüfe auf `VM-WIN-SRV`, dass die Netzwerkebenen-Authentifizierung (NLA) für RDP aktiv ist (`(Get-ItemProperty 'HKLM:\System\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp').UserAuthentication` ergibt `1`). Nimm nur `MitarbeiterA` in die Gruppe „Remotedesktopbenutzer“ auf und weise von `VM-WIN-CLIENT` aus nach, dass `MitarbeiterA` sich verbinden kann, `MitarbeiterB` jedoch abgewiesen wird.

*Ergänzung der Ausarbeitung (Einheiten 7.1 und 7.3):* (a) Erstelle eine Tabelle mit vier Protokollpaaren (unsicher / sicher, z. B. HTTP / HTTPS, Telnet / SSH) und dem Grund. (b) Starte mit dem Zertifikat aus Modul 3 auf `VM-LINUX` einen Testserver `openssl s_server -accept 8443 -cert cert.pem -key k.pem -www` und prüfe ihn von derselben VM mit `openssl s_client -connect 127.0.0.1:8443 -servername vm-linux.example.com < /dev/null`. Notiere `Verify return code`; wiederhole mit `-CAfile cert.pem -verify_hostname vm-linux.example.com`. (c) Nenne drei sichere HTTP-Header (Theorie).

## Hinweise

- Härte SSH **erst**, wenn der Schlüssel-Login funktioniert und eine zweite Sitzung offen ist, sonst sperrst du dich aus.
- Prüfe nach der Änderung die *wirksamen* Werte mit `sudo sshd -T | grep -iE "passwordauthentication|permitrootlogin"`. Zusatzdateien in `/etc/ssh/sshd_config.d/` können Werte überlagern (Fachwissen, auf Ubuntu nicht geprüft).
- Der Schlüssel in der Musterlösung ist ein Test-Schlüssel ohne Passphrase; für echte Schlüssel eine Passphrase verwenden.
- Zur Übertragung des Schlüssels aus PowerShell: Eine Pipe kann unter Windows PowerShell 5.1 Zeilenenden verändern (Fachwissen, nicht geprüft). Hilft das nicht, den Schlüssel per `scp` oder mit dem Editor in `authorized_keys` eintragen.

**Aufgabe 1 (Key-based Authentication einrichten (Passwort-Login noch aktiv)).**

```text
$ ssh-keygen -t ed25519
256 SHA256:64DB+NxcK6Ah6XDcuKNvYRmjmO8ST+JSjIh6t8kE4qE (ED25519)   (Test-Schlüssel)
$ chmod 700 ~/.ssh; chmod 600 ~/.ssh/authorized_keys
$ ssh -i id_ed25519 anna@192.168.50.20 id
uid=30033(anna) gid=30033(anna) groups=30033(anna),30002(projekt)
```
Anmeldung per Schlüssel funktioniert (Test auf Port 2222 mit Linux-Client statt Windows). Echte Ausgabe: `beispiele/m07.txt`.

**Aufgabe 2 (SSH-Härtung (Linux)).**

```text
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
$ sudo sshd -t              (keine Ausgabe)
$ sudo systemctl reload ssh   (im Container nicht ausführbar)
$ ssh -o PubkeyAuthentication=no anna@192.168.50.20
anna@192.168.50.20: Permission denied (publickey).
```
**Befund der Ausarbeitung:** Mit `PasswordAuthentication no` allein bot die minimale Testkonfiguration weiterhin `keyboard-interactive` an (Meldung `Permission denied (publickey,keyboard-interactive).`); erst die Zeile `KbdInteractiveAuthentication no` ergab `Permission denied (publickey).` Auf Ubuntu mit PAM kann sich das anders verhalten. Auch Root-Login mit Schlüssel und unbekannte Benutzer werden abgewiesen. Die Meldung „Permission denied“ des Lehrplans trifft zu.

**Aufgabe 3 (Absicherung von Remotedesktop (Windows)).** **Windows (nicht ausgeführt):** `(Get-ItemProperty 'HKLM:\System\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp').UserAuthentication` soll `1` ergeben. Gruppenmitglied: `Add-LocalGroupMember -Group "Remotedesktopbenutzer" -Member MitarbeiterA`. Erwartet: Verbindung von `MitarbeiterA` gelingt, `MitarbeiterB` wird mit einer Meldung wie „nicht für die Remoteanmeldung autorisiert“ abgewiesen (Wortlaut nicht bestätigt).

**Ergänzung (a):**

| Unsicher | Sicher | Grund |
|---|---|---|
| Telnet | SSH | Klartext gegen Verschlüsselung und Schlüssel-Login |
| HTTP | HTTPS | Mitlesen und Verändern der Daten |
| FTP | SFTP / FTPS | Kennwörter im Klartext |
| SMBv1 | SMB 3 mit Verschlüsselung | veraltetes Protokoll mit bekannten Schwächen (Fachwissen) |

**Ergänzung (b)** mit dem selbstsignierten Zertifikat:

```text
$ openssl s_client -connect 127.0.0.1:8443 -servername vm-linux.example.com < /dev/null
verify error:num=18:self-signed certificate
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
Verify return code: 18 (self-signed certificate)
$ openssl s_client -connect 127.0.0.1:8443 -CAfile cert.pem -verify_hostname vm-linux.example.com < /dev/null
Verification: OK
Verify return code: 0 (ok)
```
Ohne Vertrauensanker wird das Zertifikat abgelehnt (`curl` meldet `SSL certificate problem: self-signed certificate`). **Ergänzung (c):** `Strict-Transport-Security`, `Content-Security-Policy`, `X-Content-Type-Options` (Fachwissen).

**Fragen.** (1) Telnet überträgt alles, auch Benutzername und Kennwort, im **Klartext**. Jeder, der den Verkehr mitschneiden kann, liest die Zugangsdaten mit (siehe Mitschnitt in Modul 10). SSH verschlüsselt den Kanal und kann Schlüssel statt Kennwörter nutzen. (2) `PasswordAuthentication no` (und im Test zusätzlich `KbdInteractiveAuthentication no`), `PermitRootLogin no`, und `PubkeyAuthentication yes`. Ohne Kennwort-Login gibt es nichts zu erraten. Ergänzend begrenzen `MaxAuthTries` und eine Sperre nach Fehlversuchen Angriffe (Fachwissen). (3) Der Server weist sich mit einem Zertifikat aus, das der Client gegen seine vertrauenswürdigen CAs prüft (Kette, Gültigkeit, Hostname). Ein Mittelsmann besitzt kein gültiges Zertifikat für den Hostnamen; der Client meldet einen Fehler (im Test `self-signed certificate`). Der Schutz gilt nur, wenn die Prüfung nicht abgeschaltet wird (`curl -k`).
