## Lernziele

Nach dieser Übung kannst du

- eine Host-basierte Firewall einrichten und spezifische Ports blockieren oder freigeben
- das Konzept von Netzwerkzonen (DMZ, Intranet) und VPNs verstehen

## Voraussetzungen

- Grundlagen in IPv4 (Subnetting, RFC 1918). VMs müssen über den privaten Switch kommunizieren können

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **Stateless / Stateful** | Paketfilter ohne Verbindungsgedächtnis bzw. mit Zustandstabelle, die Antworten erlaubter Verbindungen zulässt |
| **Host-basierte Firewall** | Filter auf dem Rechner selbst (Windows Defender Firewall, UFW) |
| **DMZ** | Zone zwischen Internet und Intranet für öffentlich erreichbare Server |
| **Zero Trust** | kein Gerät und kein Benutzer gilt allein wegen seines Standorts im Netz als vertrauenswürdig |
| **VLAN** | logische Trennung eines Netzes auf Layer 2 |
| **VPN / IPsec** | verschlüsselter Tunnel über ein unsicheres Netz; IPsec ist eine Protokollfamilie dafür |
| **IDS / IPS** | Erkennungs- bzw. Verhinderungssystem für Angriffe im Verkehr |
| **Egress-Filter** | Filterung des ausgehenden Verkehrs |

## Aufgabe

### Aufgabe 1 – Windows Defender Firewall (Erweitert) (Einheit 5.1)

Aktiviere auf `VM-WIN-SRV` zuerst den Remotedesktop (Einstellungen oder `Set-ItemProperty -Path 'HKLM:\System\CurrentControlSet\Control\Terminal Server' -Name fDenyTSConnections -Value 0`). Deaktiviere die vordefinierten Regeln „Remotedesktop“, damit nur deine eigene Regel gilt. Konfiguriere danach eine eingehende Regel, die RDP (TCP-Port 3389) nur von der IP-Adresse `192.168.50.30` (`VM-WIN-CLIENT`) zulässt (z. B. `New-NetFirewallRule -DisplayName 'RDP nur von Client' -Direction Inbound -Protocol TCP -LocalPort 3389 -RemoteAddress 192.168.50.30 -Action Allow`), und eine Regel, die ICMPv4-Echoanforderungen blockiert (`New-NetFirewallRule -DisplayName 'ICMPv4 blockieren' -Direction Inbound -Protocol ICMPv4 -IcmpType 8 -Action Block`). Teste von `VM-WIN-CLIENT` aus: `ping 192.168.50.10` schlägt fehl, `Test-NetConnection 192.168.50.10 -Port 3389` ist erfolgreich. *Hinweis: Dokumentiere diese Regeln genau, sie bleiben für spätere Diagnosen (Modul 12) aktiv.*

### Aufgabe 2 – Linux UFW (Uncomplicated Firewall) (Einheit 5.1)

Erlaube auf `VM-LINUX` zuerst SSH (Port 22) und HTTP (Port 80) (`sudo ufw allow 22/tcp`, `sudo ufw allow 80/tcp`), setze die Standardrichtlinie auf „Deny Incoming“ (`sudo ufw default deny incoming`) und aktiviere erst danach die UFW (`sudo ufw enable`), damit eine bestehende SSH-Sitzung nicht abbricht. Prüfe mit `sudo ufw status verbose`.

### Aufgabe 3 – Soll-Zustand sichern (Einheit 5.1, Einheit 5.2, Einheit 5.3)

Speichere `Get-NetFirewallRule -Direction Inbound -Enabled True | Format-Table DisplayName, Action > Soll-Firewall.txt` auf `VM-WIN-SRV` und `sudo ufw status verbose > soll-ufw.txt` auf `VM-LINUX` als Vergleichsbasis für Modul 12.

*Ergänzung der Ausarbeitung (Einheiten 5.2 und 5.3, ohne Technik):* Skizziere das Labor als Netzzonen-Plan (Internet, DMZ, Intranet) und trage ein, wo bei einem echten Netz eine DMZ für `VM-LINUX` (Webserver), ein VPN-Gateway und ein IDS liegen würden. Notiere, welche Zonenübergänge du mit Firewall-Regeln absichern würdest und warum das Labor selbst nur ein flaches Netz ist.

## Hinweise

- Setze bei Remote-Konfiguration immer zuerst die Ausnahmen (Regel „Allow“) und erst dann die Sperre, sonst sperrst du dich selbst aus.
- `ufw enable` fragt nach, ob bestehende SSH-Verbindungen unterbrochen werden dürfen; im Test wurde `ufw --force enable` verwendet. Port 22 ist freigegeben, solange du SSH nutzt.
- Eine Regel „Allow“ für Port 22 ohne laufenden SSH-Dienst ergibt in Nmap „closed“, nicht „filtered“ (siehe Musterlösung).
- Dokumentiere die Regeln genau, sie bleiben für Modul 12 aktiv. Regeln der Aufgabe 1 sind nicht ausgeführt; Parameter der Cmdlets wurden auf Microsoft Learn gelesen.

## Musterlösung

<details>
<summary>Antworten und Zielzustand (erst nach dem Versuch öffnen)</summary>

**Aufgabe 1 (Windows Defender Firewall (Erweitert)).** **Windows (nicht ausgeführt):**

```text
Set-ItemProperty -Path 'HKLM:\System\CurrentControlSet\Control\Terminal Server' -Name fDenyTSConnections -Value 0
Disable-NetFirewallRule -DisplayGroup "Remotedesktop"
New-NetFirewallRule -DisplayName 'RDP nur von Client' -Direction Inbound -Protocol TCP -LocalPort 3389 -RemoteAddress 192.168.50.30 -Action Allow
New-NetFirewallRule -DisplayName 'ICMPv4 blockieren' -Direction Inbound -Protocol ICMPv4 -IcmpType 8 -Action Block
```
Erwartet von `VM-WIN-CLIENT`: `ping 192.168.50.10` schlägt fehl, `Test-NetConnection 192.168.50.10 -Port 3389` meldet `TcpTestSucceeded : True`. Der Gruppenname „Remotedesktop“ der vordefinierten Regeln ist **nicht bestätigt** (deutsche Anzeigename, bei englischem System `Remote Desktop`). Die Parameter `-Direction`, `-Protocol`, `-LocalPort`, `-RemoteAddress`, `-IcmpType` und `-Action` kennt `New-NetFirewallRule` laut Microsoft Learn; `-Direction` ist standardmäßig `Inbound`.

**Aufgabe 2 (Linux UFW (Uncomplicated Firewall)).**

```text
$ sudo ufw allow 22/tcp; sudo ufw allow 80/tcp; sudo ufw default deny incoming; sudo ufw --force enable
$ sudo ufw status verbose
Status: active
Logging: on (low)
Default: deny (incoming), allow (outgoing), disabled (routed)
New profiles: skip

To                         Action      From
--                         ------      ----
22/tcp                     ALLOW IN    Anywhere
80/tcp                     ALLOW IN    Anywhere
```
Wirkung (Nmap von `VM-WIN-CLIENT`): Port 80 `open`, Port 22 `closed` (Regel erlaubt, aber kein Dienst), Port 8080 `filtered`. Echte Ausgabe: `beispiele/m05.txt`.

**Aufgabe 3 (Soll-Zustand sichern).**

```text
Get-NetFirewallRule -Direction Inbound -Enabled True | Format-Table DisplayName, Action > Soll-Firewall.txt   (nicht ausgeführt)
$ sudo ufw status verbose > soll-ufw.txt
```
Ablage der Soll-Dateien: außerhalb der Ordner, die in Modul 12 verändert werden. 

**Zonenplan (Vorschlag):**

```text
Internet -- [Firewall] -- DMZ: Webserver (VM-LINUX, nur 80/443) -- [Firewall] -- Intranet: Dateiserver (VM-WIN-SRV), Clients (VM-WIN-CLIENT)
                 |                                                                         |
          VPN-Gateway (Remote-Access)                                               IDS am Spiegelport
```
Das Labor ist ein flaches Netz ohne Gateway; es gibt keine echte DMZ, die Host-Firewalls ersetzen hier die Zonenübergänge. Aussagen zu Zonen, VPN und IDS sind Fachwissen.

**Fragen.** (1) Eine **Stateless**-Firewall prüft jedes Paket einzeln gegen die Regeln (Adressen, Ports). Eine **Stateful**-Firewall merkt sich den Zustand von Verbindungen und lässt Antworten auf erlaubte Verbindungen automatisch zu, ohne dass dafür eine eigene Regel nötig ist. (2) Die DMZ trennt öffentlich erreichbare Server (Web, Mail) vom internen Netz. Wird ein Server in der DMZ kompromittiert, kommt der Angreifer nicht direkt ins Intranet, weil dazwischen eine weitere Firewall liegt. (3) Schadsoftware muss meist nach außen telefonieren (Befehlsserver) oder Daten hinausschicken. Wer ausgehenden Verkehr auf das Nötige begrenzt, kann diese Verbindungen blockieren und Angriffe sichtbar machen. (4) Ein **Site-to-Site-VPN** verbindet zwei Standortnetze dauerhaft über zwei Gateways; die Endgeräte merken nichts. Ein **Remote-Access-VPN** verbindet einzelne Clients (z. B. Laptop im Home-Office) mit dem Firmennetz. **IPsec** ist eine Protokollfamilie, die IP-Pakete authentifiziert und verschlüsselt (Schlüsselaustausch über IKE) und für beide VPN-Arten genutzt werden kann. (Fachwissen des Verfassers, nicht gegen eine Quelle geprüft.)
