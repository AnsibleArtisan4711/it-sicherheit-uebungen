## Lernziele

Nach dieser Übung kannst du

- die Phasen eines TLS-Verbindungsaufbaus erklären
- Cipher-Suites aufschlüsseln und interpretieren
- wesentliche Unterschiede zwischen TLS 1.2 (RFC 5246) und TLS 1.3 (RFC 8446) benennen

## Voraussetzungen

- Modul 7 (Dateien `ca.crt`, `server.crt`, `server.key`), Windows-11-VM, Linux-VM mit `tshark`

## Grundbegriffe

| Begriff | Bedeutung |
|---|---|
| **TLS** | Transport Layer Security; schützt die Verbindung zwischen Client und Server (TLS 1.2: RFC 5246, TLS 1.3: RFC 8446) |
| **Client Hello / Server Hello** | erste Nachrichten des Handshakes: Fähigkeiten des Clients bzw. Auswahl des Servers |
| **Cipher Suite** | Kombination aus Verfahren für Schlüsselaustausch, Authentisierung, Verschlüsselung und Hash |
| **Key Share** | bei TLS 1.3 im Client Hello mitgesendeter öffentlicher DH-Wert (z. B. `x25519`) |
| **PFS** | Perfect Forward Secrecy: Sitzungsschlüssel aus kurzlebigen Schlüsseln, ein späterer Schlüsselverlust entschlüsselt alte Mitschnitte nicht |
| **AEAD** | Verschlüsselung mit integriertem Integritätsschutz (z. B. AES-GCM) |
| **`tshark`** | Kommandozeilenversion von Wireshark; `-i` Schnittstelle, `-f` Aufzeichnungsfilter, `-Y` Anzeigefilter, `-r`/`-w` Datei lesen/schreiben |
| **legacy_version** | Feld im Server Hello, das bei TLS 1.3 aus Kompatibilitätsgründen `TLS 1.2 (0x0303)` zeigt; die echte Version steht in der Erweiterung `supported_versions` |

## Aufgabe

### Aufgabe 1 – Lokalen TLS-Server starten (Einheit 8.1)

Wechseln Sie auf `linux01` nach `~/krypto/m07/` und starten Sie in einem eigenen Terminal `openssl s_server -accept 4433 -cert server.crt -key server.key -www`. Die Option `-www` lässt den Server auf HTTP-Anfragen mit einer Statusseite antworten; ohne sie erhält ein Browser keine verwertbare Antwort. Der Server läuft, bis er mit Strg+C beendet wird.

### Aufgabe 2 – Handshake aufzeichnen (Einheit 8.1, Einheit 8.2)

Ermitteln Sie auf `linux01` die Netzwerkschnittstelle (`ip -br link`) und starten Sie in einem zweiten Terminal `sudo tshark -i <Schnittstelle> -f "tcp port 4433" -w ~/krypto/m08/tls13.pcapng` (Ordner vorher anlegen). Rufen Sie auf `win11-01` `curl.exe -vk https://192.168.10.10:4433/` auf (`-k` ignoriert die noch nicht vertraute CA, siehe Modul 9) und öffnen Sie dieselbe Adresse im Browser; dokumentieren Sie die Zertifikatswarnung. Beenden Sie danach den Mitschnitt mit Strg+C.

### Aufgabe 3 – Paketanalyse (Einheit 8.2, Einheit 8.4)

Werten Sie den Mitschnitt auf `linux01` aus, z. B. mit `tshark -r ~/krypto/m08/tls13.pcapng -Y "tls.handshake.type == 2" -V`. Lokalisieren Sie „Client Hello“ und „Server Hello“, notieren Sie die ausgehandelte Version und Cipher Suite und vermerken Sie, dass bei TLS 1.3 das Server-Zertifikat im Mitschnitt nicht lesbar ist (Verschlüsselung nach dem Server Hello). Die Filtersyntax kann mit `tshark -G fields` geprüft werden.

### Aufgabe 4 – TLS 1.2 vergleichen (Einheit 8.4)

Starten Sie den Server neu mit zusätzlicher Option `-tls1_2`, wiederholen Sie Mitschnitt (`tls12.pcapng`) und Aufruf und vergleichen Sie: Version, Cipher Suite, Sichtbarkeit des Zertifikats im Mitschnitt, Anzahl der Handshake-Nachrichten. Halten Sie drei Unterschiede zu TLS 1.3 schriftlich fest.

### Aufgabe 5 – Cipher Suites zerlegen (Einheit 8.3)

Zeigen Sie die ausgehandelten Suites mit `openssl ciphers -v` an (z. B. `openssl ciphers -v 'ECDHE-RSA-AES256-GCM-SHA384'`) und zerlegen Sie sie in Schlüsselaustausch, Authentifizierung, Verschlüsselung und MAC bzw. AEAD. Notieren Sie, warum TLS-1.3-Suites (z. B. `TLS_AES_256_GCM_SHA384`) keine Angabe zu Schlüsselaustausch und Signatur enthalten.

## Hinweise

- Der Server läuft in einem eigenen Terminal und blockiert es; beende ihn mit Strg+C. `ACCEPT` auf dem Bildschirm bedeutet, dass er wartet.
- Im Mitschnitt zeigt das Server Hello auch bei TLS 1.3 `Version: TLS 1.2 (0x0303)` (legacy_version). Die ausgehandelte Version steht in der Erweiterung `supported_versions` (`TLS 1.3 (0x0304)`); `curl -v` zeigt sie in der Zeile `SSL connection using TLSv1.3`.
- `-k` bei `curl` schaltet die Zertifikatsprüfung ab; das ist nur für diese Aufgabe gedacht, bevor die CA vertraut wird (Modul 9).
- Die Option `-tls1_2` am Server beschränkt ihn auf TLS 1.2; der Client verhandelt dann diese Version (die Zeile `Client hello` in `curl -v` zeigt trotzdem `TLSv1.3 (OUT)`, weil der Client TLS 1.3 *anbietet*).
- `openssl ciphers -v` zeigt immer die drei TLS-1.3-Suites mit an; die Namen von TLS-1.3-Suites lassen sich nur mit `-ciphersuites` auswählen (`openssl ciphers -v TLS_AES_256_GCM_SHA384` meldet in OpenSSL 3.0 `no cipher match`).
- Den Mitschnitt kannst du auch grafisch mit Wireshark öffnen (nicht Teil der VMs); Dateien dieser Ausarbeitung liegen in `beispiele/`.

## Kontrollfragen

1. Welche Daten sendet der Server typischerweise in der "Server Hello" Nachricht zurück an den Client?
2. Wofür steht das Konzept "Perfect Forward Secrecy" (PFS) innerhalb eines TLS-Handshakes?
3. Warum ist der TLS 1.3 Handshake in der Regel performanter als der von TLS 1.2?
4. Zerlegen Sie die Cipher Suite `ECDHE-RSA-AES256-GCM-SHA384` in ihre Bestandteile und erklären Sie, welche davon für Perfect Forward Secrecy sorgt.

**Aufgabe 1 (Lokalen TLS-Server starten).**

```text
$ openssl s_server -accept 4433 -cert server.crt -key server.key -www
Using default temp DH parameters
ACCEPT
```

Der Server wartet auf Port 4433 und beantwortet mit `-www` HTTP-Anfragen mit einer Statusseite (mit `curl` getestet: `HTTP/1.0 200 ok`).

**Aufgabe 2 (Handshake aufzeichnen).**

```text
$ ip -br link
lo      UNKNOWN  ...
eth0    UP       ...
$ sudo tshark -i eth0 -f "tcp port 4433" -w ~/krypto/m08/tls13.pcapng
$ curl.exe -vk https://192.168.10.10:4433/       (auf win11-01; Testumgebung: curl 8.5.0 unter Linux)
* TLSv1.3 (OUT), TLS handshake, Client hello (1):
* TLSv1.3 (IN), TLS handshake, Server hello (2):
* TLSv1.3 (IN), TLS handshake, Encrypted Extensions (8):
* TLSv1.3 (IN), TLS handshake, Certificate (11):
* TLSv1.3 (IN), TLS handshake, CERT verify (15):
* TLSv1.3 (IN), TLS handshake, Finished (20):
* TLSv1.3 (OUT), TLS handshake, Finished (20):
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384 / X25519 / RSASSA-PSS
< HTTP/1.0 200 ok
```

Der Name der Schnittstelle hängt von der VM ab (in der Testumgebung `eth0`); auf `linux01` mit `ip -br link` prüfen. Im Browser erscheint ohne vertrauenswürdige CA eine Zertifikatswarnung (Aussage nicht geprüft; Text und Seite hängen vom Browser ab). Die Ausgabe von `curl.exe` unter Windows (Schannel) weicht von der obigen ab, nicht bestätigt.

**Aufgabe 3 (Paketanalyse).**

```text
$ tshark -r tls13.pcapng -Y "tls.handshake.type == 2" -V | grep -E 'Handshake Type|Cipher Suite:|supported_versions|Supported Version|key_share'
            Handshake Type: Server Hello (2)
            Cipher Suite: TLS_AES_256_GCM_SHA384 (0x1302)
            Extension: supported_versions (len=2) TLS 1.3
                Supported Version: TLS 1.3 (0x0304)
            Extension: key_share (len=36) x25519
$ tshark -r tls13.pcapng -Y tls.handshake -T fields -e frame.number -e tls.handshake.type -e _ws.col.Info
4       1       Client Hello
6       2       Server Hello, Change Cipher Spec, Application Data, Application Data, Application Data, Application Data
$ tshark -r tls13.pcapng -Y "tls.handshake.type == 11" | wc -l
0
```

Ausgehandelt wurden **TLS 1.3** und die Suite `TLS_AES_256_GCM_SHA384` (Schlüsselaustausch `x25519` über `key_share`). Das Feld `Version` im Server Hello zeigt `TLS 1.2 (0x0303)`; die echte Version steht in `supported_versions`. Das **Zertifikat ist nicht lesbar**: Es gibt keine Nachricht vom Typ 11 im Klartext, weil der Server nach dem Server Hello alles verschlüsselt sendet (die vier „Application Data“-Datensätze enthalten Encrypted Extensions, Certificate, CertificateVerify und Finished). Die Filtersyntax lässt sich mit `tshark -G fields | grep tls.handshake.type` prüfen (in der Testumgebung vorhanden).

**Aufgabe 4 (TLS 1.2 vergleichen).**

```text
$ openssl s_server -accept 4433 -cert server.crt -key server.key -www -tls1_2
$ tshark -r tls12.pcapng -Y tls.handshake -T fields -e frame.number -e tls.handshake.type -e _ws.col.Info
4       1       Client Hello
6       2,11,12,14      Server Hello, Certificate, Server Key Exchange, Server Hello Done
8       16      Client Key Exchange, Change Cipher Spec, Encrypted Handshake Message
9               Change Cipher Spec, Encrypted Handshake Message
$ tshark -r tls12.pcapng -Y "tls.handshake.type == 2" -V | grep 'Cipher Suite:'
            Cipher Suite: TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384 (0xc030)
$ tshark -r tls12.pcapng -Y "tls.handshake.type == 11" -V | grep -E 'commonName|dNSName'
   rdnSequence: 1 item (id-at-commonName=Lab Root CA)
   rdnSequence: 1 item (id-at-commonName=server.example.internal)
   dNSName: server.example.internal
```

Unterschiede zu TLS 1.3 (drei davon festhalten): (1) **Version und Suite:** `TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384` nennt Schlüsselaustausch (ECDHE) und Signatur (RSA) im Namen. (2) **Zertifikat im Klartext sichtbar:** Subject, Issuer und SAN lassen sich mitlesen. (3) **Zwei Round Trips statt einem:** Client Hello, dann Server-Nachrichten (Hello, Zertifikat, Key Exchange, Hello Done), dann Client Key Exchange, Change Cipher Spec und Finished, dann die Finished-Nachricht des Servers; bei TLS 1.3 reichen Client Hello und die gesammelte Server-Antwort. (4) Bei TLS 1.2 stammt der Schlüsselaustausch aus der Server-Key-Exchange-Nachricht, bei TLS 1.3 aus `key_share` im Hello.

**Aufgabe 5 (Cipher Suites zerlegen).**

```text
$ openssl ciphers -v 'ECDHE-RSA-AES256-GCM-SHA384'
TLS_AES_256_GCM_SHA384         TLSv1.3 Kx=any      Au=any   Enc=AESGCM(256)            Mac=AEAD
TLS_CHACHA20_POLY1305_SHA256   TLSv1.3 Kx=any      Au=any   Enc=CHACHA20/POLY1305(256) Mac=AEAD
TLS_AES_128_GCM_SHA256         TLSv1.3 Kx=any      Au=any   Enc=AESGCM(128)            Mac=AEAD
ECDHE-RSA-AES256-GCM-SHA384    TLSv1.2 Kx=ECDH     Au=RSA   Enc=AESGCM(256)            Mac=AEAD
$ openssl ciphers -v -ciphersuites TLS_AES_256_GCM_SHA384 'ECDHE-RSA-AES256-GCM-SHA384'
TLS_AES_256_GCM_SHA384         TLSv1.3 Kx=any      Au=any   Enc=AESGCM(256)            Mac=AEAD
ECDHE-RSA-AES256-GCM-SHA384    TLSv1.2 Kx=ECDH     Au=RSA   Enc=AESGCM(256)            Mac=AEAD
$ openssl ciphers -v TLS_AES_256_GCM_SHA384
Error in cipher list
...:error:0A0000B9:SSL routines:SSL_CTX_set_cipher_list:no cipher match:...
```

**Zerlegung von `ECDHE-RSA-AES256-GCM-SHA384`:** Schlüsselaustausch `ECDHE` (Elliptic Curve Diffie-Hellman *ephemeral*, `Kx=ECDH`), Authentisierung `RSA` (`Au=RSA`: Signatur des Zertifikatsschlüssels), Verschlüsselung `AES256` im Modus `GCM` (`Enc=AESGCM(256)`), Hash `SHA384` (für die Schlüsselableitung; `Mac=AEAD`, weil GCM selbst authentisiert). Die TLS-1.3-Suites enthalten **keine Angabe zu Schlüsselaustausch und Signatur**, weil beides unabhängig von der Suite ausgehandelt wird (Schlüsselaustausch über `key_share`, Signaturverfahren über `signature_algorithms`); die Suite legt nur den AEAD-Algorithmus und den Hash fest (`Kx=any`, `Au=any`).

**Fragen.** (1) Das Server Hello enthält die gewählte TLS-Version (bei 1.3 in `supported_versions`), die ausgewählte Cipher Suite, eine Zufallszahl des Servers (Server Random) und, bei TLS 1.3, den eigenen Key Share (öffentlicher DH-Wert); bei TLS 1.2 folgen im selben Antwortpaket Zertifikat, Server Key Exchange und Server Hello Done. (2) PFS bedeutet, dass der Sitzungsschlüssel aus kurzlebigen (ephemeren) Diffie-Hellman-Werten entsteht, die nach der Sitzung verworfen werden. Wird später der private Schlüssel des Servers (Zertifikat) gestohlen, lassen sich aufgezeichnete Sitzungen trotzdem nicht entschlüsseln, weil dieser Schlüssel nur zum Signieren benutzt wurde. Das E in ECDHE steht für ephemeral. (3) TLS 1.3 braucht für den Handshake nur einen Round Trip statt zwei (Schlüsselinformation steht schon im Client Hello), hat weniger Nachrichten und kann bei wiederkehrenden Clients mit 0-RTT-Daten noch früher senden (Fachwissen zu 0-RTT, nicht geprüft). Zusätzlich sind unsichere Verfahren entfernt. (4) `ECDHE` = Schlüsselaustausch mit ephemeren elliptischen Kurven; `RSA` = Authentisierung des Servers mit RSA-Zertifikat/Signatur; `AES256` = Verschlüsselung mit 256-Bit-AES; `GCM` = Betriebsmodus (AEAD, authentisiert); `SHA384` = Hash für Schlüsselableitung und Handshake. **Perfect Forward Secrecy** liefert `ECDHE` (ephemeral).

</details>

- Erzwinge mit `curl --tls-max 1.2` bzw. `--tlsv1.3` eine Version und vergleiche das Verhalten.
- Starte den Server mit `-ciphersuites TLS_CHACHA20_POLY1305_SHA256` und prüfe die ausgehandelte Suite.
- Werte mit `tshark -T fields -e tls.handshake.extensions_server_name` den SNI-Namen aus dem Client Hello aus.
